02 · Idempotency — Request Deduplication + Replay

Role: safe retry of the same operation request: first call executes, repeats replay the stored result. Postgres owns the claims, Redis speeds the replays.

Contents · Ports · Table · Flow · Sequence · Layout · Config · Rules

Public port

Inject IdempotencyPort around any operation a client may retry. First call runs, repeats replay the stored result. COMPLETED results are also cached in Redis for fast replay; Postgres stays authoritative for claims.

methods
reserve({ scope, key }) → ACQUIREDYours to run. Keep the reservation for complete/fail.
reserve → REPLAY + resultAlready done. Return the stored result, run nothing.
reserve → BUSYAnother attempt is running. Answer 409 and let the client retry later.
reserve → KEY_MISMATCHSame key, different payload. Answer 400, the key belongs to another request.
complete({ reservation, result }) → voidStores the result future calls will replay.
fail({ reservation }) → voidReleases the claim so the next call starts clean.
const claim = await this.idempotency.reserve({ tenantId, organizationId, scope: 'sales.order.create', key: idempotencyKey });
if (claim.status === 'REPLAY') return claim.result;
if (claim.status !== 'ACQUIRED') throw new ConflictException();
try {
  const result = await this.createOrder();
  await this.idempotency.complete({ reservation: claim.reservation, result });
  return result;
} catch (error) {
  await this.idempotency.fail({ reservation: claim.reservation });
  throw error;
}

Flow

sequence
1reserve finds no row, INSERTs IN_PROGRESS and returns ACQUIRED with the claim. The use case executes, then complete stores COMPLETED plus resultJson with a CAS (Compare-And-Swap) on id plus token plus version, and writes the result to Redis, expiring with the row
2reserve checks the Redis result cache first: HIT returns REPLAY without touching Postgres. On MISS it reads the row, and COMPLETED with the same hash returns REPLAY with the stored result
3COMPLETED with a different hash returns KEY_MISMATCH (400, do not retry with this key)
4reserve finds IN_PROGRESS with a live lease and returns BUSY (409, retry later)
5expired lease lets the next reserve take it with a fresh token and returns ACQUIRED
6fail performs a CAS (Compare-And-Swap) delete of the row and evicts the Redis key, so the next call starts clean. Reconciler (hourly) deletes expired IN_PROGRESS plus expired COMPLETED rows.

Rules

rules
Tenant splitSame key in another tenant or organization is a different record.
Client-driven retries onlyBUSY answers 409, KEY_MISMATCH answers 400, REPLAY returns the byte-identical original.
fail() releases immediatelyNo parking lot. Crashed claims are taken over after the lease expires.
Keys are not business idsOne scope per operation. Never reuse a key across different operations.
Postgres owns claims, Redis speeds replays.IN_PROGRESS claims live only in Postgres so concurrent reserves always collide on the unique constraint. Only COMPLETED results are cached, so cache and row expire together.
