07 · Inbox — Consumer-Side Deduplication

Role: consumer counterpart of Outbox. Guarantees same logical message + same consumer gives one business execution under at-least-once redelivery. No business rules, no broker knowledge.

Contents · Ports · Table · Flow · Compare · Sequence · Layout · Config · Rules

Public port

Inject InboxPort at the top of every broker or event consumer. Only ACQUIRED proceeds to the listener.

methods
receive({...}) → ACQUIRED + reservationFirst delivery wins. Pass consumer name plus the envelope ids.
receive → DUPLICATEAlready processed. Return without touching the listener.
receive → BUSYIn flight, suspended, or not due for retry. Return and wait for redelivery.
complete({ reservation }) → voidMarks it done. Broker ACK (acknowledgement) happens only after this.
fail({ reservation, error? }) → voidKeeps it pending with backoff for the next attempt.
const delivery = await this.inbox.receive({ consumer: 'inventory.reserve',
  messageId: message.headers['event-id'], messageType: message.eventType, payload: message.payload });
if (delivery.status !== 'ACQUIRED') return;
await this.requestContext.run(requestIds, async () => {
  try {
    await this.reserveUseCase.execute(message.payload);
    await this.inbox.complete({ reservation: delivery.reservation });
  } catch (error) {
    await this.inbox.fail({ reservation: delivery.reservation });
    throw error;
  }
});

Flow (listener template)

sequence
1Broker delivers the message to the listener (@RabbitSubscribe, @KafkaEvent, @SqsMessageHandler, or @OnEvent).
2inbox.receive with the consumer name plus the envelope ids. ACQUIRED proceeds, DUPLICATE or BUSY returns.
3requestContext.run restores tenant, company, correlation, and causation before business code runs.
4The reserve use case executes the payload, then inbox.complete marks it done, then the broker ACK (acknowledgement) fires.
5Failure calls inbox.fail to keep it pending with backoff, then the broker NACK (negative acknowledgement) triggers redelivery.
6Reconciler (60 seconds): expired IN_PROGRESS lease plus attempts over max becomes SUSPENDED (alertable), otherwise stays IN_PROGRESS with nextAttemptAt backoff. The same sweep deletes PROCESSED rows past retention.

Config

env
INBOX_CLAIM_LEASE_MS300000 — processing window before the reconciler may free the claim
INBOX_MAX_ATTEMPTS5 — failures past this park the message as SUSPENDED
INBOX_RETRY_BASE_DELAY_MS / INBOX_RETRY_MAX_DELAY_MS5000 / 600000 — exponential backoff between attempts
INBOX_RECONCILIATION_INTERVAL_MS60000 — sweep for expired claims
INBOX_PROCESSED_RETENTION_MS2592000000 — PROCESSED rows older than 30 days are deleted; FAILED and SUSPENDED never purge

Rules

rules
Tenant splittenant plus company plus consumer plus messageId is the identity.
Acknowledge in orderBroker ACK (acknowledgement) only after inbox.complete. fail triggers NACK (negative acknowledgement) and redelivery.
Listeners stay re-runnableThe same message can arrive twice around crashes; guard side effects accordingly.
Poison is parked, not droppedPast max attempts the message waits SUSPENDED for alert plus manual recovery. Finished PROCESSED rows purge past retention; parked ones never do.
Effects leave via OutboxAny event the consumer produces is appended in the same transaction.
