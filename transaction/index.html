Transaction Management via the nestjs-cls Prisma Adapter

No hand-rolled manager. The official ClsPluginTransactional + TransactionalAdapterPrisma owns prisma.$transaction, stores the tx client in CLS, and exposes it as txHost.tx. One decorator, full commit-or-rollback flow.

01 — Mental model

Adapter replaces the custom manager

Before: you wrote TransactionManager + TX_CLIENT_KEY + interceptor yourself. After: the plugin does exactly that — tested and nested-safe. Your code only touches two things: @Transactional() and txHost.tx.

Without / with adapter
  • Without — service injects PrismaService directly. Second write fails, first stays. Corrupt data.
  • With adapter — @Transactional() on service method → plugin opens $transaction → every txHost.tx shares it → commit or rollback.
  • User → controller (thin) → service @Transactional() → ClsPluginTransactional → TransactionalAdapterPrisma → CLS tx → repos via txHost.tx → Postgres

Rule stays: never inject PrismaService in services or repos. Inject TransactionHost and use txHost.tx — inside a transaction it is the tx client, outside it is the plain client.

Alt — outcome
Success: COMMIT → controller returns 201 Created. Error at 5/6/7: ROLLBACK → no partial rows → exception filter maps to 500 / 4xx.
Wire key — the rust lifeline is txHost.tx. Steps 4–8 all hang off it. Nested @Transactional() joins the same wire by default (Propagation.Required).
03 — Request lifecycle

Request → plugin → CLS → txHost → Prisma

  1. 1
    Request → Controller (thin)
    POST /orders calls the service. No decorator here — the transaction boundary lives on the service method so it covers all writes.
  2. 2
    @Transactional() → ClsPluginTransactional
    Plugin wraps the method. Checks CLS: tx already active? Join it. Otherwise ask the adapter to start one.
  3. 3
    Adapter → prisma.$transaction
    TransactionalAdapterPrisma calls $transaction(async (tx) => …) with your timeout / isolation options. Holds the real BEGIN/COMMIT/ROLLBACK.
  4. 4
    CLS stores tx, txHost exposes it
    Plugin puts tx in CLS. txHost.tx returns it; txHost.isTransactionActive() is true. Every async child of the request sees it.
  5. 5
    UoW + repos → txHost.tx
    Repositories call this.txHost.tx.user.create(). Outside a transaction the same line uses the plain client — no branching needed.
  6. 6
    Commit / rollback
    Resolve → adapter COMMITs. Throw → adapter ROLLBACKs and rethrows. CLS slot is cleared so the next request starts clean.
04 — Install + plugin setup

Wire the adapter once at the root

// install
// npm i @nestjs-cls/transactional @nestjs-cls/transactional-adapter-prisma
// (v2 and earlier: adapter ships inside @nestjs-cls/transactional)

// prisma.module.ts — exposes PrismaService for the adapter
import { Global, Module } from '@nestjs/common';
import { PrismaService } from './prisma.service';

@Global()
@Module({ providers: [PrismaService], exports: [PrismaService] })
export class PrismaModule {}

// app.module.ts
import { Module } from '@nestjs/common';
import { ClsModule } from 'nestjs-cls';
import { ClsPluginTransactional } from '@nestjs-cls/transactional';
import { TransactionalAdapterPrisma } from '@nestjs-cls/transactional-adapter-prisma';

@Module({
  imports: [
    PrismaModule,
    ClsModule.forRoot({
      global: true,
      middleware: { mount: true }, // one CLS context per request
      plugins: [
        new ClsPluginTransactional({
          imports: [PrismaModule],
          adapter: new TransactionalAdapterPrisma({
            prismaInjectionToken: PrismaService,
            // txOptions: { timeout: 10000, maxWait: 5000 },
          }),
        }),
      ],
    }),
  ],
})
export class AppModule {}

The adapter needs the same PrismaService instance your app uses — hence prismaInjectionToken + listing PrismaModule in imports.

05 — Adapter deep-dive

What TransactionalAdapterPrisma actually does

Responsibilities
  • Lifecycle — owns start / commit / rollback via prisma.$transaction callback form
  • connectionTokenTxProxy — maps TransactionHost.tx to tx-client-inside / plain-client-outside
  • isTransactionActive — reports whether CLS currently holds a tx for this request
  • options passthrough — timeout, maxWait, isolationLevel forwarded to $transaction
  • propagation — Required joins existing tx; RequiresNew suspends it and opens a fresh one
No custom keys — you never call cls.get('TX_CLIENT') yourself. The adapter owns the CLS key internally; txHost.tx is the only read path.
06 — Unit of Work

Thin wrapper around TransactionHost

UoW keeps service code expressive (uow.users / uow.orders) while every repo shares the adapter's tx.

// common/transaction/unit-of-work.service.ts
import { Injectable } from '@nestjs/common';
import { UserRepository } from '../../modules/users/user.repository';
import { OrderRepository } from '../../modules/orders/order.repository';
import { PaymentRepository } from '../../modules/payments/payment.repository';

@Injectable()
export class UnitOfWork {
  constructor(
    public users: UserRepository,
    public orders: OrderRepository,
    public payments: PaymentRepository,
  ) {}
}

// orders.service.ts — the transaction boundary
import { Injectable } from '@nestjs/common';
import { Transactional } from '@nestjs-cls/transactional';

@Injectable()
export class OrdersService {
  constructor(private uow: UnitOfWork) {}

  @Transactional() // plugin + adapter open the tx here
  async create(dto: CreateOrderDto) {
    const user = await this.uow.users.create(dto.user);
    const order = await this.uow.orders.create({ ...dto, userId: user.id });
    await this.uow.payments.charge(order.id, dto.amount);
    return order;
  }
}

// orders.controller.ts — stays thin, no decorator needed
import { Body, Controller, Post } from '@nestjs/common';

@Controller('orders')
export class OrdersController {
  constructor(private orders: OrdersService) {}
  @Post()
  create(@Body() dto: CreateOrderDto) {
    return this.orders.create(dto);
  }
}
07 — @Transactional()

Options you will actually use

import { Propagation, Transactional } from '@nestjs-cls/transactional';

// default: join existing tx, else open one
@Transactional()
create(dto: CreateOrderDto) { /* ... */ }

// pass Prisma tx options through the adapter
@Transactional({ timeout: 10000, maxWait: 5000, isolationLevel: 'ReadCommitted' })
importBulk(dto: BulkDto) { /* ... */ }

// open a fresh tx even inside one (audit log that must persist)
@Transactional({ propagation: Propagation.RequiresNew })
audit(entry: AuditDto) { /* ... */ }

// read-only intent: still joins, signals no writes expected
// (adapter does not enforce it — keep the method write-free by convention)
@Transactional({ propagation: Propagation.Required })
getWithLock(id: string) { /* ... */ }
CaseDecorator
Standard use-case (join or open)@Transactional()
Long import, avoid Prisma timeout@Transactional({ timeout, maxWait })
Must commit even if outer rolls back@Transactional({ propagation: RequiresNew })
Programmatic check in codetxHost.isTransactionActive()
08 — Repository

Only layer that touches the tx client

// modules/users/user.repository.ts
import { Injectable } from '@nestjs/common';
import { TransactionHost } from '@nestjs-cls/transactional';
import { TransactionalAdapterPrisma } from '@nestjs-cls/transactional-adapter-prisma';

@Injectable()
export class UserRepository {
  constructor(
    private txHost: TransactionHost<TransactionalAdapterPrisma>,
  ) {}

  // inside @Transactional(): the tx client. Outside: the plain client.
  private get db() {
    return this.txHost.tx;
  }

  create(data: any) {
    return this.db.user.create({ data });
  }
  findById(id: string) {
    return this.db.user.findUnique({ where: { id } });
  }
}

09 — Folder structure

Less code than the hand-rolled version

  • common/prisma/prisma.service.ts
  • common/prisma/prisma.module.ts
  • common / transaction — only UoW lives here now
  • common/transaction/unit-of-work.service.ts
src / modules
  • modules / users, orders, payments — repository per aggregate via txHost
  • modules/users/user.repository.ts
  • modules/orders/orders.controller.ts + orders.service.ts + order.repository.ts
  • modules/payments/payment.repository.ts
  • app.module.ts — ClsModule + ClsPluginTransactional + TransactionalAdapterPrisma

Deleted vs hand-rolled: no transaction-manager.service.ts, no transaction.interceptor.ts, no transactional.decorator.ts, no TX_CLIENT_KEY. The plugin + adapter own all of it.

10 — Mistakes & practices

Adapter-specific pitfalls

MistakeFix
Injecting PrismaService in a service/repoInject TransactionHost; use txHost.tx (bypassing it silently leaves the tx)
@Transactional() on controller AND servicePut it on the service method only; nesting joins anyway but one boundary is clearer
Array-form $transaction thinkingAdapter uses callback form; dependent writes just await sequentially on txHost.tx
